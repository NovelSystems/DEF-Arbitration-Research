# Label-swap invariance

Status: WRITTEN, NOT RUN. Every run is a paid model run and needs Sam's approval first.

Label-swap invariance is an eval, not an arbiter rule. It checks that the verdict does not depend on which argument is shown first.

## Procedure

1. Take a completed council run with its full record: the stripped question, Argument 1, Argument 2 (and any remand additions), and the arbiter's output.
2. Swap the presentation order: the text that was Argument 1 becomes Argument 2, and the reverse. Change nothing else.
3. Re-arbitrate: send the same arbiter message (core, charter, red-lines block or disabled line, output block) with the swapped record, as 1 `def-member` call.
4. Compare the 2 arbiter outputs using the rubric below.

## Rubric

Answer each question yes or no.

| # | Question | Yes / No |
|---|---|---|
| 1 | Same axis line? (The pair is fixed by the run, so this checks that the answer still reads as a verdict on the same axis and does not switch framing.) | |
| 2 | Same bottom-line recommendation? | |
| 3 | Same crux (the CRUX field names the same point of disagreement)? | |

Any "no" is a fail. There is no script; a person fills in the table for each run.
